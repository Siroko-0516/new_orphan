길잡이 소프트웨어 작동 원리 설명서

전체 원리 · 교수 질의응답 · 발표문 · 코드 및 검증 근거

작성일: 2026년 11월 15일 / 설명 기준: Android 0.9.4, 정식 UNO v5

이 문서는 앞서 설명한 17개 항목, 예상 질문·답변 16개, 발표문과 근거를 하나로 정리한 문서다. 구현 내용, 일반적인 기술 원리, 실제로 검증한 범위를 구분한다. 기존 검사 기록을 새로운 실기 시험 결과로 바꾸어 제시하지 않는다. 부록에는 이번에 다시 읽은 코드의 구체적인 설정도 수록했다.

1. 길잡이는 어떤 시스템인가?

길잡이는 카메라와 휴대폰의 AI 분석 기능을 흰지팡이에 연결하여, 주변 정보를 음성과 서보모터의 움직임으로 전달하는 보행 보조 시스템이다. 물리 버튼으로 음성비서를 호출하여 현재 위치와 주변 병원을 물어보고, 연락처에 저장된 사람에게 전화를 요청할 수도 있다.

전체 흐름은 영상 입력 → 주변 상황 인식 → 안내 여부 판단 → 음성·모터 출력 → 사용자 명령 실행이다.

의자가 보이는 경우에도 다음은 서로 다른 문제다.

-   인식: 영상에 의자가 있는가?
-   판단: 그 의자가 사용자의 진행을 방해할 가능성이 있는가?
-   안내: 지금 말해야 하는가? 이미 안내한 상황인가?
-   출력: 어떤 문장을 읽고 어떤 모터 신호를 보낼 것인가?

YOLO는 주로 물체 인식을 담당한다. 진행 방해 여부와 안내 시점은 추가 판단이 필요하다.

발표에서는 다음처럼 소개할 수 있다.

  길잡이는 사전 학습된 시각 AI를 활용해 주변 정보를 인식하고, 이를 음성·물리 알림과 휴대폰 기능으로 연결한 보행 보조 시스템입니다. 핵심은 물체를 찾는 것뿐 아니라 반복 안내를 줄이고, 필요한 정보를 사용자가 화면을 보지 않고 확인하도록 통합한 데 있습니다.

2. 전체 구성과 각 요소의 역할

  ----------------------------------------------------------------------------------------------------
  구성 요소               맡은 역할                                  쉽게 이해하면
  ----------------------- ------------------------------------------ ---------------------------------
  ESP32-CAM               주변 영상 촬영·전송                        눈

  휴대폰 앱               영상 처리, AI 호출, 상태 관리, 장치 연결   시스템을 관리하는 중심

  YOLO11n                 물체 종류와 영상 안의 위치 추정            물체를 빠르게 찾는 기능

  로컬 VLM                기기 안에서 이미지 해석·설명 생성          사진을 보고 설명하는 기능

  Gemini·GPT              인터넷을 통한 이미지·음성·대화 처리        외부 AI 분석 서비스

  TTS                     문장을 음성으로 변환                       목소리

  HM-10                   휴대폰과 UNO 사이의 BLE 데이터 전달        짧은 신호를 전달하는 통신 장치

  Arduino UNO             버튼 입력 처리, 서보모터 제어              물리 장치 제어기

  SG90                    정해진 각도로 움직여 물리 알림 제공        움직임으로 정보를 전달하는 장치

  Android 기기 API        위치·연락처 조회와 통화 실행               실제 휴대폰 기능
  ----------------------------------------------------------------------------------------------------

ESP32-CAM과 UNO가 주요 AI 모델을 실행하는 중심 장치는 아니다. 주요 분석은 휴대폰 또는 클라우드에서 수행한다.

    ESP32-CAM ── Wi-Fi 영상 ──> 휴대폰 앱
                                 ├─ 선택한 영상 분석 경로
                                 ├─ 안내 내용·반복·작업 상태 관리
                                 ├─ TTS → 무선이어폰
                                 └─ BLE → HM-10 → UNO → 서보모터

    물리 버튼 → UNO → HM-10 → 휴대폰 음성비서

이것은 기능 구성도다. 모든 모델을 매번 동시에 실행한다는 뜻은 아니다. 실제 분석 경로는 모드와 설정에 따라 달라진다.

3. 카메라 영상은 어떻게 AI 입력이 되는가?

카메라 영상을 신경망이 이해하는 숫자 배열로 바꾸는 과정이 필요하다.

    촬영 → 영상 데이터 수신 → 이미지 디코딩
         → 크기·색상·배열 변환 → 모델 입력 → 결과 해석

이미지 디코딩

JPEG는 이미지를 압축하여 저장·전송하는 형식이다. 앱은 이를 풀어 각 픽셀의 색상 값을 얻는다. MJPEG는 여러 JPEG 프레임을 연속해서 보내는 방식이다. 초당 여러 프레임이 들어온다고 AI가 모두 같은 속도로 분석한다는 뜻은 아니다.

전처리

모델은 정해진 입력 규격을 요구한다. 이 프로젝트의 YOLO 모델은 416×416 입력 기준으로 내보내졌다. 이미지 크기, RGB 채널 순서, 픽셀 값 범위, 채널·높이·너비의 배열 순서, 가로세로 비율과 여백을 맞춰야 한다.

입력 색상 순서 등이 맞지 않으면 모델 파일이 정상이어도 결과가 나빠질 수 있다. 현재 Android 코드에서는 비율을 유지해 크기를 조정하고 여백을 넣는 letterbox 전처리를 사용한다. RGB 값을 255로 나누고, 채널별로 나눈 배열을 모델에 전달한다.

프레임 관리

입력이 분석보다 빠르면 처리 대기 영상이 쌓일 수 있다. 보행 안내에서는 오래된 프레임을 차례로 처리하기보다 최신 상황을 반영하는 것이 중요하다. 이미 지나간 의자를 뒤늦게 안내하면 설명이 맞더라도 현재 행동에는 도움이 되지 않을 수 있다. 촬영 시각, 작업 취소, 이전 응답의 무효화 같은 상태 관리가 필요한 이유다.

4. YOLO는 어떻게 물체를 찾는가?

YOLO는 You Only Look Once의 약자다. 한 번의 신경망 전방 계산에서 여러 물체 후보의 위치와 종류를 예측하는 객체 탐지 계열 모델이다. 한 번이라는 말이 신경망이 한 층이라는 뜻은 아니다.

길잡이 모델은 YOLO11n이다. n은 nano, 즉 작은 모델 계열을 뜻한다. 작은 모델은 연산·메모리 부담을 줄이는 데 유리하지만, 작은 물체나 복잡한 상황의 인식에는 한계가 있을 수 있다.

① 이미지에서 특징을 추출한다

앞쪽 단계에서 경계·질감·모양 등의 특징을 추출하고, 뒤쪽 단계에서 이를 조합해 물체를 구분하는 표현을 만든다. 특징 추출 부분을 백본, 서로 다른 크기의 특징을 결합하는 부분을 넥, 최종 예측 부분을 검출 헤드라고 부른다. 여러 해상도의 특징을 활용하면 가까운 큰 물체와 멀리 있는 작은 물체를 함께 다루는 데 도움이 된다.

② 물체 종류와 상자를 예측한다

모델은 물체를 둘러싸는 바운딩 박스와 종류에 대한 점수를 출력한다.

    물체: 의자 / 클래스 점수: 0.87 / 영상 안의 사각형 위치

0.87을 곧바로 “정답일 확률이 87%”라고 해석하면 안 된다. 모델 점수와 현실의 정답률이 정확히 일치하도록 보정되었다고 보장할 수 없기 때문이다.

③ 낮은 점수의 후보를 걸러낸다

기준을 높이면 불확실한 탐지는 줄지만 실제 물체를 놓칠 수 있다. 기준을 낮추면 후보는 늘지만 잘못된 탐지도 늘 수 있다. 오탐과 미탐 사이의 균형 문제다.

④ 겹치는 중복 상자를 정리한다

한 물체를 여러 후보 상자가 둘러쌀 수 있다. 대표적인 중복 제거 방법이 NMS, 비최대 억제다. 상자의 겹침 정도는 IoU로 나타낸다.

    IoU = 두 상자의 교집합 면적 ÷ 두 상자의 합집합 면적

같은 종류의 상자가 많이 겹치면 높은 점수의 상자를 남기는 식으로 중복을 줄인다. 현재 코드도 ONNX 출력 뒤에 NMS를 수행한다.

NMS와 반복 음성 억제는 서로 다르다. NMS는 한 프레임의 중복 상자를 정리하고, 반복 음성 억제는 여러 시점의 비슷한 안내를 줄인다. NMS만으로 같은 의자에 대한 안내가 한 번만 나오지는 않는다.

YOLO의 중요한 한계

이 모델은 COCO 기반 사전 학습 모델로 기본 80개 물체 범주를 다룬다. “COCO 물체를 인식한다”와 “모든 보행 위험을 인식한다”는 다른 주장이다. 계단, 작은 단차, 바닥의 파임 같은 요소가 기본 범주로 충분히 표현되지 않을 수 있다. 의자를 찾았다는 사실만으로 진행 경로를 방해한다고 확정할 수도 없다.

5. ONNX와 ONNX Runtime은 무엇인가?

  용어            의미
  --------------- -------------------------------------------
  YOLO11n         물체 탐지 모델 계열
  학습된 가중치   학습으로 얻은 숫자 매개변수
  ONNX            모델의 계산 구조와 가중치를 표현하는 형식
  ONNX Runtime    ONNX 모델을 실제로 계산하는 실행 엔진

YOLO는 모델, ONNX는 이를 담는 형식, ONNX Runtime은 실행 엔진으로 구분하면 된다. ONNX 변환은 새로 학습하는 것이 아니라 다른 실행 환경에서 추론할 수 있도록 계산 구조를 내보내는 과정이다.

ONNX Runtime을 사용한다고 GPU·NPU가 자동으로 사용되는 것은 아니다. 실제 실행 장치를 확인해야 한다. 이번에 읽은 Android YoloDetector는 CPU 경로이며, 스레드 설정은 연산 내부 2개, 연산 간 1개다. 이를 로컬 VLM의 Vulkan 실행 여부와 혼동하면 안 된다.

6. 로컬 VLM은 YOLO와 무엇이 다른가?

VLM은 Vision-Language Model, 이미지와 언어를 함께 다루는 모델이다. YOLO가 “의자·상자·점수”를 출력한다면 VLM은 “앞쪽 통로에 의자가 놓여 있습니다”와 같은 문장을 생성할 수 있다. 자연스러운 문장이 곧 정확한 사실이라는 뜻은 아니다.

Android 배포 기록에는 MiniCPM 1B 계열 로컬 VLM과 별도 비전 가중치가 포함되어 있다.

    이미지 → 비전 인코더 → 이미지 특징 벡터
           → 언어 모델에 맞춘 변환 → 언어 모델 → 설명 문장

비전 인코더는 이미지를 작은 영역이나 특징 단위로 처리해 숫자 벡터로 바꾼다. 이 표현은 모양과 주변 관계 등을 다루는 데 사용된다.

특징 연결 부분은 이미지 특징을 언어 모델이 사용할 수 있는 표현으로 연결한다. 모델에 따라 projector나 resampler 등이 사용된다. mmproj라는 이름만 보고 작은 변환 행렬만 들어 있다고 단정하면 안 된다. 배포 구성에 따라 비전 가중치도 포함될 수 있다.

언어 모델은 이미지 특징과 질문을 바탕으로 다음 토큰을 예측하는 과정을 반복한다.

    P(다음 토큰 | 이미지 특징, 질문, 이전에 생성한 토큰)

단색 화면에서 엉뚱한 설명이 나오는 이유

이미지 정보가 부족해도 학습된 문장 패턴에 따라 그럴듯한 답을 생성할 수 있다. 이를 환각, hallucination이라고 한다. 단색 화면을 보고 “계단이나 단차가 위험하다”는 일반 조언을 했다면 실제 계단을 확인한 결과라고 볼 수 없다.

-   실제 영상에서 확인한 내용
-   가능성이나 추측
-   일반적인 보행 조언

이 세 가지를 구분해야 한다. 보행 안내는 실제 관측에 근거해야 하고, 불확실한 설명을 위험 발견처럼 전달하지 않아야 한다. 흐림·가림·단색 점검은 도움이 되지만 단색이라는 이유로 주변이 안전하다고 확정할 수도 없다.

7. GGUF·JNI·C++·Vulkan은 각각 무엇인가?

GGUF와 실행 메모리

GGUF는 가중치와 관련 정보를 저장하는 형식이다. 로컬 추론 엔진이 이를 읽어 모델을 실행한다.

  배포 파일                          기록된 크기
  ------------- --------------------------------
  model.gguf         672,003,680바이트, 약 672MB
  mmproj.gguf     1,110,117,984바이트, 약 1.11GB

내장 모델을 포함한 APK는 약 1.83GB다. 파일 크기와 실행 메모리 사용량은 같지 않다. 중간 계산 결과, 문맥 캐시와 작업 버퍼 등이 추가로 필요하다.

JNI와 C++

JNI는 Java와 C/C++ 코드를 연결하는 인터페이스다. Android 서비스·화면·권한을 관리하는 코드가 JNI를 통해 네이티브 추론 엔진을 호출한다.

    Android 앱 코드 → JNI → C/C++ 추론 엔진

JNI 자체가 AI 판단을 하거나 자동으로 속도를 높이는 것은 아니다. 기존 네이티브 엔진과 최적화된 수치 계산을 활용하는 연결 수단이다.

양자화

가중치를 더 적은 비트로 표현하여 저장 공간과 메모리 부담을 줄이는 기술이다. 예를 들어 16비트에서 4비트로 표현하면 가중치 데이터의 이론적인 저장량은 줄어든다.

하지만 실제 양자화 형식, 장치의 계산 효율, 품질 변화, 비전 인코더에도 같은 최적화가 적용됐는지는 별개다. 언어 모델만 압축해도 비전 인코더가 느리면 이미지 분석 시간은 길 수 있다. 이 예시는 특정 배포 파일이 반드시 해당 방식이라는 단정이 아니다.

Vulkan

Vulkan은 GPU 계산에 활용할 수 있는 저수준 API다. 다음은 서로 다른 사실이다.

1.  GPU 실행 기능이 빌드에 포함됐다.
2.  실행할 때 그 기능이 선택됐다.
3.  주요 연산이 GPU에서 수행되어 속도가 개선됐다.

길잡이 APK에 Vulkan 구성 요소가 있다는 사실만으로 실제 휴대폰의 가속 효과까지 입증할 수는 없다.

8. Gemini·GPT는 앱에서 어떻게 사용되는가?

    앱이 이미지·음성 등 입력 준비 → HTTPS 요청
    → 제공자 모델 처리 → 응답 수신
    → 앱에서 결과 해석·검사 → 안내 또는 기기 기능 처리

Gemini·GPT가 휴대폰의 카메라·GPS·연락처를 저절로 읽는 것은 아니다. 앱이 권한을 얻고 필요한 데이터를 준비해야 한다. 이전 사진을 비교하려면 해당 사진이나 이전 정보를 요청에 포함해야 한다. AI가 모든 과거 영상을 자동으로 기억한다고 설명하면 안 된다.

응답은 예를 들어 다음처럼 전달할 수 있다.

    {"speak":true,"message":"앞쪽 통로에 의자가 보여요.","urgency":"notice"}

speak는 발화 제안, message는 문장, urgency는 긴급도 구분이다. JSON은 전달 규약이다. 형식이 맞다고 내용까지 사실임을 보장하지 않는다. 앱에서 내용과 작업 상태, 안내 정책을 함께 확인해야 한다.

HTTP 오류 이해

  코드   대표적인 확인 항목
  ------ --------------------------------
  400    요청 형식·입력 조건
  403    인증·접근 권한
  404    모델명·요청 경로·제공 여부
  429    요청 속도·사용량 제한
  503    서버 혼잡·일시적인 서비스 장애

503이 반드시 잘못된 API 키를 뜻하지는 않는다. 또한 ESP 카메라 Wi-Fi 연결과 인터넷 연결은 별개다. CloudNetwork는 이런 환경에서 인터넷 경로를 선택하는 역할을 맡는다.

9. 언제 말하고 언제 조용히 있어야 하는가?

물체 탐지와 별도의 안내 정책이 필요하다.

    첫 프레임 의자 3개 → 다음 프레임 2개 → 그다음 3개

가림·흔들림·점수 변화로 상자 수가 달라질 수 있다. 개수 변화만으로 새로운 안내가 필요한 상황이라고 볼 수는 없다.

-   이미 안내한 상황인가?
-   새로운 방해 요소가 등장했는가?
-   진행에 영향을 줄 변화인가?
-   오래된 영상의 결과는 아닌가?
-   사용자가 음성비서와 대화 중인가?
-   작업이나 안내가 취소됐는가?

반복 안내 억제와 작업 상태 관리는 이러한 문제를 다룬다. 안내가 없다는 것은 발화를 선택하지 않았다는 뜻이며, 주변 안전이 확인됐다는 뜻은 아니다.

영상 중앙과 진행 방향

지팡이를 휘두르면 카메라 방향도 바뀔 수 있다. 영상 중앙과 사용자의 이동 방향이 항상 같지는 않다. 장착 각도·흔들림·이동 방향을 고려해야 하며, 현재 구현을 완전한 실제 공간 좌표 추정으로 설명하면 안 된다.

정확히 전방 2m라고 말하기 어려운 이유

일반 카메라의 2차원 영상만으로는 거리 추정에 불확실성이 있다. 단순한 카메라 모델에서는 다음 관계를 사용할 수 있다.

    거리 ≈ 초점거리 × 실제 물체 높이 ÷ 영상 속 물체 높이

실제 높이와 카메라 조건을 알아야 한다. 의자 종류나 촬영 각도가 달라지면 오차가 커진다. 정확한 거리를 목표로 한다면 깊이 센서·스테레오 카메라·보정된 지면 모델 등 추가 방법과 실측 검증이 필요하다. 이는 현재 기능과 향후 개선 사항을 구분할 부분이다.

10. 로컬 AI가 느린 이유와 속도 평가

    T전체 = T영상수신 + T전처리 + T이미지처리
          + T문장생성 + T음성시작

영상 수신, JPEG 디코딩, 비전 인코더, 문장 생성, TTS 준비 중 어디가 느린지 나눠 측정해야 한다.

기존 호스트 실행 기록은 다음과 같다.

  단계            기록된 시간
  ------------- -------------
  준비                1.566초
  이미지 처리        11.785초
  문장 생성           0.717초

이 수치는 휴대폰 보행 성능 측정값이 아니다. 해당 실행에서 이미지 처리가 큰 비중을 차지했다는 근거다.

이미지 처리만 40초가 걸린다면 문장을 줄이거나 번역만 바꾸는 것으로 전체를 2초로 줄일 수 없다. 입력 해상도·이미지 분할 수·비전 인코더 크기·실제 GPU 실행·초기화 재사용·데이터 복사·메모리·문맥 길이·출력 토큰·최신 프레임 처리·발열을 검토해야 한다.

YOLO 처리 시간과 VLM 처리 시간은 별도로 평가한다. YOLO와 규칙의 빠른 알림을 생성형 VLM 자체의 빠른 장면 해석으로 설명하면 측정 대상이 달라진다.

  “2초 이하를 목표로 하지만 실제 휴대폰의 전체 VLM 처리를 그 수준으로 검증한 상태는 아닙니다. 단계별 측정이 필요하며 기존 기록에서는 이미지 처리 단계가 주요 병목입니다.”

11. 음성비서는 어떻게 듣고 말하는가?

  기능                    의미
  ----------------------- ---------------------------
  음성 인식·오디오 이해   사용자가 말한 내용 해석
  TTS                     답변 문장을 음성으로 변환

음성 입력 처리라는 논리적 단계가 있다고 별도의 STT 전용 모델을 항상 호출한다는 뜻은 아니다. 선택한 AI의 오디오 처리 방식에 따라 달라진다.

    대기 → 버튼 누름 → 녹음 → 버튼 다시 누름
    → 전송·해석 → 응답 음성 → 대기

    답변 중 버튼 누름 → 재생 중단 → 새 녹음

현재 방식은 말소리만으로 자동 중단하는 방식이 아니라 버튼으로 대화 차례를 조작한다. 녹음·전송을 구분하고, 취소된 응답의 재생을 막고, 출력 음성이 재입력되는 일을 줄이며, 여러 버튼 입력에 상태가 꼬이지 않도록 관리해야 한다.

TTS 선택

-   로컬 장면 AI: 휴대폰 기본 한국어 TTS만 사용.
-   Gemini·GPT 음성비서: ElevenLabs 사용 가능.
-   ElevenLabs 오류·지연: 기본 TTS 대체.
-   기본 TTS에는 사용할 수 있는 한국어 음성이 준비되어 있어야 함.

TTS는 문장을 읽으며 문장의 사실 여부를 검증하는 역할은 아니다.

12. 위치·주변 병원·전화는 누가 실행하는가?

AI 언어 처리와 Android 실제 기능 실행을 분리한다.

현재 위치

    “내 위치가 어디야?” → 위치 명령 분류
    → Android 위치 API로 좌표 확인
    → 주소 서비스로 변환 → 확인한 주소를 음성 안내

위도·경도 좌표와 도로명 등의 주소는 다르다. 좌표를 주소로 바꾸는 작업은 역지오코딩이다. Android Geocoder를 사용하고 실패하면 Nominatim 조회를 시도한다. 주소를 얻지 못하면 추측하지 않고 실패를 설명해야 한다.

주변 병원

    현재 좌표 → 지도 데이터에서 병원·의원 검색
    → 시설 이름·좌표 확인 → 대략적인 거리 계산 → 음성 안내

관련 경로는 Overpass와 Nominatim을 사용한다. AI가 기억으로 만든 병원 이름과 실제 지도 조회는 구분해야 한다. 등록된 병원 위치, 현재 진료 여부, 응급 진료 가능 여부, 걸어서 이동할 거리는 각각 별개다. 대략적인 직선거리만으로 모두 확인했다고 말할 수 없다.

전화

    “전화해줘” → “누구에게 전화할까요?” → 이름 입력
    → 연락처 검색 → “엄마에게 전화할까요?”
    → 질문 재생 완료 → 명확한 긍정
    → 연결 안내 완료 → Android 발신 요청

부정·불명확한 답변·질문 종료 전 긍정·만료·인식 오류·권한 부족·연결 안내 중 취소에는 발신하지 않도록 처리한다. 확인 동의는 한 번만 사용한다. 질문 재생 완료 후 최대 60초, 생성 시점부터 최대 120초의 상한을 둔다.

앱이 확인하는 것은 재생 시작·완료 이벤트다. 실제 사용자가 들었다는 사실까지 측정하지는 않는다. 발신은 TelecomManager 등 Android 기능이 수행한다. AI가 “전화했습니다”라고 말한 것만으로 실제 통화 연결이 입증되지는 않는다.

13. BLE·UART·UNO·서보모터 연결 원리

    휴대폰 ↔ HM-10       : BLE
    HM-10 ↔ Arduino UNO : UART 직렬 통신
    UNO → SG90          : 서보 제어 펄스

BLE

적은 데이터를 저전력으로 주고받기 위한 블루투스 방식이다. 앱은 장치의 서비스와 특성(characteristic)을 찾아 데이터를 쓰거나 알림을 구독한다. 실제 모듈과 앱 설정이 일치해야 한다.

영상 전체를 HM-10으로 보내는 것은 아니다. 영상은 Wi-Fi, 장치 제어·버튼은 BLE, 이어폰 음성은 휴대폰 오디오 연결을 사용한다. HM-10은 이어폰 역할을 하지 않는다.

UART와 배선

HM-10과 UNO 사이의 유선 직렬 통신이다. 정식 v5 기준은 다음과 같다.

  항목         연결
  ------------ --------------------------
  HM-10 TXD    UNO D0, RX
  UNO D1, TX   분압 등을 거쳐 HM-10 RXD
  서보 신호    D2
  버튼 신호    D3
  GND          공통 접지

송신과 수신은 교차한다. UNO의 5V 출력과 HM-10 입력 전압 조건을 구분해야 한다. 정식 v5의 UART는 9600 기준이며 진단 스케치 시리얼 모니터 속도와 혼동하지 않아야 한다. D0·D1은 USB 시리얼과 공유하므로 업로드 충돌도 고려한다.

명령 구분

  명령       목적
  ---------- ---------------
  TEST       모터 시험
  OBSTACLE   모터 알림
  ASSIST     음성비서 호출

줄바꿈으로 명령 끝을 구분한다. 버튼은 ASSIST 용도이며 모터 시험과 연결하지 않는다. BLE 쓰기 완료만으로 서보의 실제 움직임까지 입증되지는 않는다. 무선 전달·UART 수신·명령 해석·전원·실제 구동을 구분해야 한다.

SG90

목표 각도를 제어하는 서보모터로 무한 연속회전 DC 모터와 다르다. 펄스 폭에 따라 목표 위치가 달라지고 내부 제어 회로가 그 위치에 접근하도록 움직인다. 대표적으로 약 20ms 주기의 펄스를 쓰지만 허용 폭과 각도 범위는 제품·라이브러리 조건을 확인해야 한다.

Servo 라이브러리는 타이머로 펄스를 생성하므로 D2에 analogWrite용 PWM 표시가 없어도 제어할 수 있다. 빨강은 전원, 갈색은 GND, 주황은 신호다. 신호 핀으로 모터 전력을 공급하는 것은 아니다. 구동 중 전원 강하는 보드 재시작이나 통신 문제처럼 나타날 수 있다.

14. Android 앱·카메라 웹 앱·문의 사이트의 차이

  구분               구성과 목적
  ------------------ -------------------------------------------
  Android 앱         카메라·BLE·음성비서·위치·연락처·통화 통합
  카메라 웹 앱       브라우저에서 카메라와 웹용 AI 사용
  소개·문의 사이트   프로젝트 설명·사용법·FAQ·문의·QR

웹 로컬 AI는 SmolVLM-256M과 NLLB 한국어 번역 경로를 사용한다. Android의 MiniCPM 네이티브 실행과 같은 모델이 아니다. 브라우저는 WebGPU 지원·탭 상태·HTTPS 권한의 영향을 받으며 Android 백그라운드 서비스와 다르다.

문의 사이트는 카메라 분석을 실행하지 않는다. HTML·CSS·JavaScript로 정보를 표시하고 GitHub 문의 화면으로 연결한다. QR도 AI가 아니라 URL을 규격에 맞는 흑백 패턴으로 인코딩·해독하는 기능이다.

15. 검증한 것과 아직 입증하지 않은 것

  ----------------------------------------------------------------------------------------------
  항목                    기존 검증                             확대해서 주장하면 안 되는 내용
  ----------------------- ------------------------------------- --------------------------------
  자동 검사               0.9.4 단위 검사 332개 통과            모든 보행 위험 발견

  추가 검사               관련 68개 재검사 통과                 독립적인 400개 검사라고 합산

  위치 실행               주입한 가상 GPS 좌표 수신·갱신        실제 실외 GPS 성능 측정

  통화 실행               Android 통화 등록·전화 화면           실제 상대방 수신·연결

  확인 로직               재생 이벤트를 모의한 긍정·부정·취소   음성 대화 전체의 실기 검증

  로컬 모델               호스트의 실제 모델 실행               휴대폰에서 2초 이하 달성

  문의 사이트             화면·작성 연결·QR 해독                자체 이메일 접수 서버 운영
  ----------------------------------------------------------------------------------------------

단위 검사는 프로그램 분기와 상태 처리를 확인한다. 실제 보행 성능은 별도의 데이터와 실험이 필요하다.

추가 평가에서는 실제 방해물 누락, 잘못된 안내, 반복 빈도, 촬영부터 음성 시작까지 지연, 밝기·역광·흔들림·가림의 영향, 사용자의 이해와 구별 여부를 측정해야 한다.

    정밀도 = 올바른 탐지 ÷ 전체 탐지
    재현율 = 올바른 탐지 ÷ 실제 탐지 대상

보행에서는 진행 방해 요소를 놓친 비율과 불필요한 음성 안내 빈도도 중요하다. 공식 YOLO 데이터셋 수치를 실제 보행 정확도로 대체하면 안 된다.

16. 교수님 예상 질문과 답변

① YOLO를 직접 개발하거나 학습시켰나요?

“현재는 사전 학습된 YOLO11n을 활용했습니다. 새로 학습한 모델이라고 주장하는 것은 아니며 영상 입력·탐지 결과 처리·안내 정책·BLE와 휴대폰 기능을 통합한 부분이 개발 범위입니다.”

② 의자를 찾았다고 왜 위험하다고 할 수 있죠?

“물체 종류만으로 위험을 판단할 수는 없습니다. 진행 방향과의 관계, 새로운 변화와 현재 상황을 함께 봐야 합니다. 탐지와 보행 위험 판단을 구분합니다.”

③ YOLO가 있는데 VLM을 쓰는 이유는 무엇인가요?

“YOLO는 정해진 물체를 빠르게 찾는 데 적합합니다. VLM은 이미지와 언어를 연결해 관계나 설명을 생성할 수 있지만 계산 비용과 환각 문제가 있어 역할이 다릅니다.”

④ 전방 2m라고 어떻게 측정했나요?

“현재 일반 영상으로 정확한 2m를 측정했다고 검증한 상태는 아닙니다. 카메라 보정이나 깊이 정보 등 추가 방법과 실측 평가가 필요합니다.”

⑤ 지팡이가 흔들리면 진행 방향도 틀어지지 않나요?

“맞습니다. 영상 중앙과 이동 방향이 항상 같지는 않습니다. 장착 각도와 스윙을 고려해야 하며 완전한 실제 공간 좌표 추정으로 설명하지 않습니다.”

⑥ 같은 장애물을 계속 말하면 왜 안 되나요?

“탐지 결과의 작은 변화와 새로운 정보 발생은 다릅니다. 반복 안내는 정보 부담을 늘리므로 장면 변화와 이전 안내를 고려해 발화 여부를 관리합니다.”

⑦ 로컬이면 전화와 병원 검색도 인터넷 없이 되나요?

“로컬은 장면 분석 경로를 뜻합니다. 클라우드 음성 처리와 지도 조회에는 인터넷이 필요하며 실제 전화는 통신망과 권한에 의존합니다.”

⑧ GPU를 쓰는데 왜 느리죠?

“GPU 지원이 포함된 것과 주요 연산이 실제 GPU에서 빠르게 수행되는 것은 다릅니다. 실행 경로·지원 연산·복사·메모리를 확인하고 단계별로 측정해야 합니다.”

⑨ AI가 마음대로 전화할 수 있나요?

“핵심 명령은 앱이 분기합니다. 연락처에서 대상을 찾고 대상 이름을 읽는 확인 질문이 끝난 뒤 유효한 긍정 응답이 있어야 Android 발신 기능을 호출합니다.”

⑩ AI가 GPS에 직접 접근하나요?

“앱이 Android 위치 API로 좌표를 받습니다. 주소와 병원도 관련 서비스의 조회 결과를 사용하며 AI가 스스로 위치를 안다고 가정하지 않습니다.”

⑪ 이어폰과 HM-10을 같이 연결해도 되나요?

“HM-10은 BLE 제어 데이터, 이어폰은 휴대폰 오디오 연결을 사용해 역할이 다릅니다. 실제 동시 사용과 음성 입출력 경로는 기기에서 확인해야 합니다.”

⑫ D2는 PWM 핀이 아닌데 서보가 움직이나요?

“Servo 라이브러리가 타이머로 펄스를 생성하므로 analogWrite용 PWM 표시 핀만 사용해야 하는 것은 아닙니다.”

⑬ 테스트 통과면 실제 보행에 안전한가요?

“자동 검사는 상태 처리와 기능 실행의 근거입니다. 실제 위험 인식률과 보행 안전은 별도 현장·사용성 평가가 필요합니다.”

⑭ 사진과 음성은 어디로 가나요?

“로컬 분석은 기기에서 수행하고 클라우드 AI에는 필요한 입력을 전송합니다. 지도 조회에는 좌표가, ElevenLabs에는 읽을 문장이 전달될 수 있습니다.”

⑮ 기존 AI 연결이라면 개발 기여는 무엇인가요?

“입력부터 출력까지의 시스템 통합입니다. 영상·장치 통신, 반복 안내 억제, 버튼 상태, 취소, 위치·연락처 명령 분기, 확인 후 전화와 검증 체계를 통합했습니다.”

⑯ 오픈소스 모델이면 자유롭게 상업화할 수 있나요?

“모델과 라이브러리마다 조건이 다릅니다. YOLO는 AGPL 또는 별도 라이선스를, 웹 NLLB는 비상업적 사용 조건을 확인해야 합니다. 구성 요소별 확인이 필요합니다.”

17. 발표 시작에 사용할 설명문

  길잡이는 카메라와 AI를 흰지팡이에 연결한 보행 보조 프로젝트입니다. ESP32-CAM 영상을 휴대폰에서 받아 선택한 AI 경로로 분석하고 필요한 정보를 음성과 서보모터 움직임으로 전달합니다.

  YOLO는 물체의 종류와 위치를 찾고, VLM은 이미지를 바탕으로 설명을 생성합니다. 물체 인식이 바로 위험 판단이 되는 것은 아니므로 반복 안내와 상황 변화를 관리하는 단계가 필요합니다.

  버튼으로 음성비서를 호출할 수 있습니다. 위치와 연락처는 Android 기능으로 확인하고 전화는 대상 이름과 동의를 확인한 뒤 발신합니다.

  자동 검사와 가상 기기의 위치·통화 실행 검사를 수행했습니다. 실제 보행 위험 인식 성능, 휴대폰 지연과 사용자에게 전달되는 효과는 별도의 실기 평가가 필요합니다.

기억할 구분은 물체 탐지(무엇이 어디에 보이는가), 장면 해석(어떤 상황인가), 안내 정책(지금 무엇을 전달하는가), 기기 실행(어떤 권한·확인을 거치는가), 검증(어느 환경에서 어디까지 확인했는가)다.
